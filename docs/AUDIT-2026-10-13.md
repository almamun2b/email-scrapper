# Email Scraper: Code Audit 2

**Date:** 2026-10-13 · **Fixes applied:** 2026-10-13 (see the Status column and [Fix notes](#fix-notes)) · **Previous audit:** `docs/AUDIT.md` (2026-10-03, all findings fixed; in git history)
**Scope:** all of `src/`, `scripts/`, `test/`, CI and the docs, including the then-uncommitted v3 resume work (`--retry-rate-limited`, `--retry-budget-queued`, `scripts/mark-budget-from-logs.ts`).

## How the audit was done

- Read every source, script and test file.
- `npm run typecheck` passed, `npm test` passed (93 tests), and `npm audit` reported 0 vulnerabilities. A few packages were a minor version behind.
- Probed suspected bugs with throwaway scripts (robots-parser origin handling, extraction edge cases, `net.BlockList` with IPv4-mapped addresses).
- Mined the caches (3,926 sites, 20,491 email rows) and `logs/error-*.log` for real-world problems.

## Owner decisions (2026-10-13)

1. Emails found on many sites that don't own them go to a separate file, `emails/<category>/shared/<name>.csv`, with the same columns.
2. The name fallback is person name, then department page title, then the input CSV's `name` column, then the scraped business name.
3. Everything below is implemented, in the order of the phases.

## Bugs

### B1. robots.txt is ignored on the site's other origins (Reproduced)

**Where:** [robots.ts](../src/robots.ts) `allowed()`, [crawler.ts](../src/crawler.ts) `SiteCrawl.enqueue()` and the redirect check in `runQueue()`.

`robots-parser` answers `undefined` when asked about a URL whose origin differs from the robots.txt it parsed. `allowed()` treats anything but `false` as allowed. `crawlable()` counts `www.` and the bare host, `http:` and `https:`, and other ports as the same site. So a link from `https://x.com/` to `https://www.x.com/private` is fetched although `x.com/robots.txt` says `Disallow: /private`, and the www host's own robots.txt is never read. The same applies to redirect targets. This breaks the owner's rule to respect robots.txt.

Probe: `isAllowed('https://example.com/private/x')` → `false`; the `www.` and `http:` forms → `undefined`.

**Fix:** check each page against the robots.txt of its own origin (loaded once per origin, which also registers that origin's Crawl-delay) just before it is fetched, and again for a redirect target.

### B2. The browser phase ignores Crawl-delay and the per-server limits

**Where:** [browser.ts](../src/browser.ts) fetcher vs [http.ts](../src/http.ts) `hostLimit`/`waitTurn`.

Every plain-HTTP request waits for a per-server slot and the server's gap (Crawl-delay or 429 backoff). The browser fetcher calls `page.goto` directly, so in Phase 2 a `Crawl-delay: 10` site gets two pages at a time with no gap, and a server answering 429 isn't slowed. README and CLAUDE.md both say Crawl-delay is honoured.

**Fix:** run each browser navigation inside the same per-server slot and gap, and feed its status into the 429/503 backoff.

### B3. A retry that finds fewer emails throws the new ones away (confirmed in code)

**Where:** [index.ts](../src/index.ts) `processFile`: `if (prev && r.emails.length < prev.emails.length) r = prev`.

A re-crawled row is compared to the old one by count only. If the new crawl finds 9 emails and the old row had 10, the new row is discarded, including any addresses the old row didn't have. Worse, rows marked from the logs (pre-v3, `budgetQueued` set by `mark-budget-from-logs.ts`) keep that mark when they win, so every later `--retry-budget-queued` re-crawls them from the start again, for the full budget, forever. The churches retry running during this audit was doing exactly that.

**Fix:** merge the two results: the union of emails (a named hit wins), with the new crawl's resume state, counters and error.

### B4. Emails are credited to the wrong site (found in the caches)

**Where:** [output.ts](../src/output.ts) `buildRows()`: first site in input order wins.

BYD dealer sites embed a dealer-locator JSON with every dealer's addresses, so `sales@bydcastlehill.com.au` is found on 17 BYD sites and credited to whichever comes first in the list. 13,000+ cached rows have an email domain different from the site's.

**Fix:** credit an email to the site whose registrable domain matches the email's, then to the first site where it wasn't only found in raw HTML, then to the first site.

### B5. The hard timeout can still lose everything a site found

**Where:** [index.ts](../src/index.ts) `runSite()`, [http.ts](../src/http.ts) `once()`, [browser.ts](../src/browser.ts) fetcher.

At the hard limit the site's `AbortSignal` fires and the scrape gets 30 s to return. But a request queued for a server slot (held by other sites' requests on the same server) or for one of the 4 browser slots keeps waiting, and a running `page.goto` isn't cancelled. If that takes longer than the grace period, `runSite` falls back to an empty result, which also drops the emails Phase 1 found.

**Fix:** make the slot waits abortable, close the browser page on abort, and let `runSite` fall back to the last partial result (reported after the HTTP phase) instead of an empty one.

### B6. A browser context that died with Chromium is reused (seen in the logs)

**Where:** [browser.ts](../src/browser.ts) `makeBrowserFetcher()`.

`logs/error-2026-10-03.log` has two sites failing in the same millisecond with `browserContext.newPage: Target page, context or browser has been closed`. The relaunch logic only covers creating a context. A context that dies afterwards stays cached, and `newPage()` (outside the `try`) throws for every remaining page of the site.

**Fix:** on a closed-target error from `newPage()`, drop the cached context and retry once on a fresh one.

### B7. Hitting the page cap silently drops the queue (found in the caches)

**Where:** [crawler.ts](../src/crawler.ts) `runQueue()` / `leftover()`.

697 of the 3,926 cached sites (18%) fetched 400 pages or more, so they hit `--max-pages`. Their remaining queue is discarded, the summary says nothing, and the only way to go deeper is a full re-crawl.

**Fix:** save the queue when the cap is hit, report a `Capped` line in the summary, and continue those sites with `--retry-capped --max-pages=N` (F4).

### B8. Sitemap URLs with `&` are broken

**Where:** [sitemap.ts](../src/sitemap.ts).

`<loc>` values are used as written, so `?a=1&amp;b=2` becomes a parameter named `amp;b`. Any page URL containing "sitemap" is fetched as a sitemap and then dropped as a page.

**Fix:** decode the five XML entities; decide sitemap vs page by the root element (`<sitemapindex>` vs `<urlset>`).

### B9. A robots.txt server error excludes the site forever

**Where:** [robots.ts](../src/robots.ts), [cache.ts](../src/cache.ts) retry predicates.

A 5xx robots.txt correctly means "keep out" (RFC 9309), but it is recorded as `robots-disallowed`, which every retry flag skips because a real disallow won't change. A temporary 503 (maintenance, a Cloudflare challenge) therefore excludes the site permanently.

**Fix:** report it as `robots-unavailable`, which `--retry-failed` picks up.

|---|---|---|---|
| S1 | [browser.ts](../src/browser.ts) | The private-address guard is a `page.route`. Popups opened with `window.open`, service-worker requests and WebSockets bypass it. | Route on the context, block service workers, guard WebSockets with `routeWebSocket`, close popups. |

This also halves DNS lookups. |

| S4 | outputs | `emails/` is created with the default umask, so the personal data in it is world-readable on a shared machine. | Create group folders 0700 and output files 0600. |

Still good: Chromium sandbox, formula-safe CSV cells, 0 known vulnerabilities, no secrets in the repo or its history, linear regexes, per-file locks.

## Fix notes

Everything above was implemented on 2026-10-13, each with tests (`npm test`: 93 → 125 tests, no network apart from one `.invalid` DNS lookup). Baselines still hold: `lumino.co.nz` gives its 6 emails including "Craig Kirkland" (and now reports `capQueued`, since it reaches the 400-page cap), and `adhb.health.nz` gives `robots-disallowed`. An end-to-end run on a 4-row sample exercised the attribution, input names, failure details, `--dry-run`, `--retry-capped` and `--check-mx`.

Where the implementation differs from the plan, or has limits:

- **B3 (owner instruction during the work):** a re-crawled row is not merged symmetrically. The old row stays exactly as it was (its emails, names, links, business name and landing URL), and only emails the re-crawl found that the old row lacks are added. The crawl state (`resume`, `budgetQueued`, `capQueued`, `rateLimited`, `v`) comes from the re-crawl, so a log mark doesn't send the row into every later retry. If the re-crawl never reached the site, its error isn't put on the kept row.
- **B1:** redirect hops are checked before they're requested in the HTTP phase. In the browser, Chromium follows redirects itself, so a disallowed redirect target is caught only after it loaded (and its page is discarded).
- **B13:** only the `--retry-*` flags skip inputs without an output. `--summary-only` still rebuilds an input that has a cache but no output, since that needs no network.
- **D1:** an email counts as shared on 3+ distinct sites (by registrable domain) when none of them owns its domain. On the existing caches, `recheck-cache.ts` reports 83 such emails, including manufacturer and regulator boilerplate (`foacust1@ford.com` on 136 Ford sites, `gmsvcare@gm.com` on 53 GM sites, `enquiries@oaic.gov.au`). It also catches real dealer addresses from BYD's dealer-locator data for dealers that aren't in the input list (`sales@bydalbionpark.com.au` on 17 sites). They're in `shared/`, not lost.
- **B4:** on the caches, 222 emails would be credited to a different site than before, almost all BYD dealer addresses moving to their own dealer.
- **D2:** on the caches, 55 cached rows (about 30 distinct addresses) would be dropped, all placeholders or a domain-parking page's `privacy@above.com`.
- **D3 / owner decision 2:** 3,714 rows across 10 lists with a name column would be named from the input.
- **S1** has no automated test: the tests have to allow private addresses to reach their local server, so they can't exercise the guard in Chromium.
- **S2:** the HTTP phase now connects only to the addresses the guard checked. The browser still does its own DNS, so DNS rebinding remains possible in Phase 2 in principle.
- **S4:** only files and folders created from now on are owner-only; existing outputs keep their permissions.
- **P2:** `UV_THREADPOOL_SIZE` is set by the `npm run scrape` script (POSIX shells); runs started another way keep Node's default of 4.
- **Existing outputs aren't rebuilt.** Run `npx tsx scripts/recheck-cache.ts` to preview, then `npm run scrape -- --summary-only` when you want the new rules (attribution, `shared/`, input names, junk filters) applied to them.
